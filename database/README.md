## Migration system (Supabase CLI — since T-29 / Phase 4)

Migrations live in **`supabase/migrations/<timestamp>_<name>.sql`** and are applied
with **`supabase db push`**, which tracks applied versions per environment in
`supabase_migrations.schema_migrations` and runs **only the pending ones, in
order**, each inside its own transaction. **The files in version control are the
single source of truth — never the live database.**

The pipeline (`.github/workflows/deploy.yml`) runs `db push` automatically:
pushing `dev` migrates the dev/QA project, pushing `master` migrates production —
always **before** the app is published, so schema and app ship together.

### Authoring a migration

1. Create the file:
   ```
   npx supabase migration new <snake_case_description>
   ```
2. Write only the **incremental** changes (ALTER TABLE, new policy, `CREATE OR
   REPLACE FUNCTION`, …). Keep statements idempotent where practical
   (`IF NOT EXISTS`, `DROP ... IF EXISTS`, guarded `DO $$ ... $$`). Start with a
   header comment: what/why + the backlog item ID.
3. Apply to the dev/QA project while developing:
   ```
   npx supabase link --project-ref <dev-ref>    # once per machine
   npx supabase db push
   ```
4. **Commit the migration in the same commit as the code that depends on it.**
   The CI re-push on merge is a no-op for what dev already has, and QA/prod pick
   the migration up on their own pushes.

To see where an environment is: `npx supabase migration list` (local vs linked
remote), or in SQL: `select * from supabase_migrations.schema_migrations;`.

### Setting up a fresh environment

`supabase link` + `supabase db push` — the baseline migration creates the entire
v1.4.0 schema (including the `on_auth_user_created` trigger on `auth.users`,
appended manually because `db dump` does not capture auth-schema objects).
Remaining per-project setup (cron, Vault secret, Auth settings, Edge Function
secrets) is Dashboard work — follow `supabase/README.md`.

### Legacy: the V001–V010 era (frozen)

Until v1.4.0, migrations were `database/migrations/VNNN__*.pgsql` applied
manually via the SQL Editor and tracked in **`public.schema_migrations`** (V005).
Both are now **frozen as immutable history**: the files never grow, the table is
never written again. All three environments had V001–V010 applied before the
cutover; the baseline migration is their CLI-era equivalent, marked as already
applied on existing environments via `supabase migration repair`.

### Restoring from a snapshot

`database/snapshots/` holds dated **schema** dumps (tables + triggers + policies +
functions, no data) runnable directly in the SQL Editor or via `psql`. Refresh
after each production deploy (command + Windows path gotcha: `supabase/README.md`).
**Schema only in git** — data backups use the gitignored `*.dump.sql` name and
never enter the repo.

## Conventions

| Convention | Rule |
|---|---|
| File names | `supabase/migrations/<timestamp>_snake_case_description.sql` (generated by `supabase migration new`) |
| Ordering | Timestamp order; `db push` applies pending ones ascending |
| Tracking | `supabase_migrations.schema_migrations`, maintained by the CLI (the legacy `public.schema_migrations` is frozen) |
| Schema | All application tables live in `public` |
| Identity columns | `GENERATED BY DEFAULT AS IDENTITY` |
| Timestamps | Always `timestamp with time zone DEFAULT timezone('utc', now())` |
| RLS | Enabled on every table; family-scoped policies via `get_my_family_id()` (V008+) |
| Audit writes | `activity_logs` is populated exclusively by the `SECURITY DEFINER` trigger — no client-facing write policy |
| Rollback | No down-migrations — fix forward with a new corrective migration |
